Gensever Obsession

This is probably my favorite Elixir gotcha. It has its roots in people learning about Elixir, Erlang, OTP, Genservers and Supervision trees and be like: "Oh, in Elixir I gotta use tons of Genservers to be a real Elixir developer!" And then what happens is usually one of 2 things:

  1. Genservers are used for code organization, think instead of calling + to add two numbers, you create a Genserver to do this. This creates unnecessary overhead and overly complex code. This one is so sneaky, it even made its way into the beta version of an Elixir book once upon a time.
  2. People think they need to use Genservers, so they create a global Genserver to funnel all their requests through - creating an artificial bottleneck.

There are a bunch of other pitfalls, but these are the 2 main ones that I've seen.

I believe the problem is best encapsulated I had with a very senior engineer after introducing Elixir & Phoenix at work a long time ago: "We're still using this like Rails, we're not making use of any of the advanced features like Genservers or Processes!" What sounds like a complaint, is actually a compliment in my mind. Because we are using them, you just don't have to deal with them! Every request is already run in its own process. Ecto has its own pool for database connections. You get all the benefits of these great features without any hassle, as others had already put in the work.

This is a complex and nuanced topic, if you want to know more I wrote a blog post about this exact topic (5 years ago! 🤯). The biggest take away comes from Adopting Elixir though, namely what to use Genservers for:

  • Model state accessed by multiple processes.
  • Run multiple tasks concurrently.
  • Gracefully handle clean startup and exit concerns.
  • Communicate between servers.

You can't pin ^map.field

Pattern matching is one of the coolest features of Elixir, we can extract values or also make sure values are the same:

iex> %{name: name} = %{name: "Tobi"}
%{name: "Tobi"}
iex> name
"Tobi"
iex> %{name: "Tobi"} = %{name: "Tobi"}
%{name: "Tobi"}
iex> %{name: "Tobias"} = %{name: "Tobi"}
** (MatchError) no match of right hand side value: %{name: "Tobi"}
    (stdlib 5.1.1) erl_eval.erl:498: :erl_eval.expr/6
    iex:4: (file)
iex> %{name: ^name} = %{name: "Tobi"}
%{name: "Tobi"}
iex> %{name: ^name} = %{name: "Tobias"}
** (MatchError) no match of right hand side value: %{name: "Tobias"}
    (stdlib 5.1.1) erl_eval.erl:498: :erl_eval.expr/6
    iex:5: (file)

With the pin operator we can make sure we only get matches if the value in the variable matches the value in the structure we're matching. This often comes in handy especially in tests, where we use assert expected_structure = value. Now let's say I had a Person struct and I wanted to match its name against the same map we used above:

iex> defmodule Person, do: defstruct [:name]
iex> tobi = %Person{name: "Tobi"}
iex> tobi.name
"Tobi"
iex> %{name: ^tobi.name} = %{name: "Tobi"}
error: invalid argument for unary operator ^, expected an existing variable, got: ^tobi.name
└─ iex:12

** (CompileError) cannot compile code (errors have been logged)
iex> tobi_name = tobi.name
iex(13)> %{name: ^tobi_name} = %{name: "Tobi"}
%{name: "Tobi"}

As you can see %{name: ^tobi.name} does not work as it expects an existing variable and this isn't a variable. We need to assign the value to tobi_name and then we can match on it as expected. This looks and feels a bit cumbersome. The example may seem contrived, but I see it in a lot of tests for instance when you want to check which record is returned from the database and so you want to match on record.id:

target = insert_record()

# ...

# does not work:
assert %{id: ^target.id} = find_record()

# does work, but cumbersome
target_id = target.id
assert %{id: ^target_id} = find_record()

# a bit nicer imo, hat tip to @LostKobrakai
assert %{id: found_id} = find_record()
assert found_id == target.id

Why is it like this? Well, as the error indicates it's not a variable but an expression, albeit a very simple one. It's syntax sugar for "assertive" access to atom keys of structs/maps that raises when the key isn't present. And what does map.key boil down to? Well, I couldn't find it but thankfully my friend Michał helped me! It basically boils down to this (with the transformation happening here):

case map do
    %{:field => tmp} -> tmp
    %{} -> :erlang.error({:badkey, :field})
    atom when is_atom(atom) -> apply(atom, :field, [])
end

All that said, yes you need to do a little workaround to make that match work as you can only pin variables in these matches. That said, IANALD (I am not a language designer) but I wished the compiler just made that record_id = record.id extraction under the hood itself so that the initial code could work. But it's probably either hard or has some undesirable consequences :)

nil, true and false are all atoms

Coming from other languages it's easy to assume that nil has some kind of special type/class and that true and false are booleans. And well, they are all some syntax sugar on top of atoms:

iex> nil == :nil
true
iex> true == :true
true
iex> is_atom(nil)
true
iex> is_atom(true)
true

This can be an issue if nil, true or false get caught in an is_atom/1 guard clause. However, generally speaking that should be rare. As atoms should be known at compile time, do not dynamically create them, business logic code should usually check against a list of known good atoms.

iex> my_atom = :admin
:admin
iex> my_atom in [:guest, :user, :admin]
true

Hence, while this is a gotcha I haven't seen it cause bugs in production (yet). Btw. if you want to make something is indeed a boolean, there is also an is_boolean/1 guard.

alias vs require vs. import vs. use

This one doesn't cause bugs but usually quite a bit of confusion. Many other languages have one way to make other modules available: import in JavaScript, require in Ruby etc. So, why do we need 4 of them in Elixir? Well for one, that comparison isn't quite fair as these pull more weight than the ones I mentioned before. Especially in the beginning it can be confusing which one to use when, so let me give you a small overview (full guide here):

  • alias - Allows you to use another, often simpler, name to refer to a module, for instance alias MyApp.MyContext.Thing allows you to refer to just Thing instead of the whole name space.
  • require - Allows you to use the macros defined in a macro, these are opt-in as opposed to functions. Some of the most common usages here are require Logger and require IEx.
  • import - Makes functions (and macros!) available without any namespacing so instead of Thing.function() you can just use function(). In practice you see this rarely outside of using well known libraries (import Ecto.Query), as most elixir devs prefer to not obscure the origin of the function they are calling.
  • use - The most complex of the bunch, basically it involves the module any code into your module which it has defined within its __using__/1 callback. It could setup a bunch of alias, require and imports - but it can also straight up define functions. People may hate me for this, but it's a bit like inheritance in that you get a bunch of functionality from the "parent". Just that the code is basically copied into your module, and it happens less often. If you wanna see what kind of code may be copied in, ExUnit.Case is a common example.

In practice, most of what you'll likely use (esp. outside of frameworks) is just plain old alias and you get used to them all rather quickly!
